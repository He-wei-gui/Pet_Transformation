# 蜕变记 · Pet Transform —— 项目总结

## 一、项目背景与目标

「蜕变记」是一款面向**爬行宠物（守宫、蜥蜴、蛇等）**养护场景的成长记录应用。爬宠养护有几个普通宠物 App 不覆盖的痛点：

- **喂食/换底材有固定周期**，但漏一次就乱，需要"自动顺延"而不是死板的固定日历；
- **蜕皮、温湿度、UVB** 等爬宠专属指标需要长期记录；
- 养主常在**手机（鸿蒙）和微信小程序**两端切换，希望看到同一份数据。

项目目标：做一个**多端共享数据、爬宠专属、可演示完整闭环**的成长记录系统，并在鸿蒙端（ArkTS/ArkUI）实现完整的客户端体验。

## 二、最终成果

一个可运行的 HarmonyOS 应用 + 一套与微信小程序共享的 PHP 云端后端，实现：

1. **账号体系**：账号密码注册/登录、**邮箱验证码注册**、**邮箱找回密码**；密码服务端哈希、JWT 会话。
2. **宠物与记录**：宠物增删改查、喂食/称重/换料打卡、蜕皮、环境记录、数据统计。
3. **核心排程**：动态计算下次喂食/换料日期，漏打卡自动纠偏，三色紧急度。
4. **媒体能力**：云端成长相册（含高清缩放查看器）、主页相册自动轮播、本地成长视频播放。
5. **个性化**：头像可上传自定义照片、中英双语、浅深主题。

## 三、技术亮点

| 亮点 | 说明 |
|------|------|
| **在线优先的混合架构** | 核心数据上云多端共享，未上云模块走本地 SQLite；仓储层方法名统一，UI 与数据源完全解耦 |
| **严格分层 + 源无关仓储** | `UI → service → repository → (ApiClient / SQLite)`，日后任何表上云只换仓储实现，service/UI 不动 |
| **零第三方依赖** | 图表用原生 `Canvas` 手绘；图片上传手拼 multipart；SMTP 手写极简协议；全程只用系统 Kit |
| **动态排程算法** | "下次 = 实际打卡 + 间隔"，避免欠账堆积，比固定日历更贴合真实养护 |
| **增量且不破坏现网** | 邮箱功能全部以"加可空列 + 加新路由 + 新表"方式落地，微信小程序零感知 |
| **安全意识** | 密码服务端 `password_hash`；SMTP 授权码只存服务器 `.env`，绝不进客户端/公开仓库；验证码服务端校验、限频、一次性 |
| **完整 i18n / 主题** | 资源键驱动，中英文与浅深色资源成对维护 |

## 四、关键难点与解决

1. **多端数据一致** → 后端统一按 JWT 的 `openid` 隔离；鸿蒙账号可绑定到同一 `openid`，与微信端共享数据。
2. **主键类型差异**（本地自增 number vs 云端 hex string）→ 全端标识符统一为字符串，本地附属表外键改 TEXT。
3. **找回密码必须能写回云端密码** → 新增极小后端接口 `/auth/reset-password`，验证码客户端触发、服务端校验。
4. **发邮件的密钥安全** → 选择服务端发信，授权码进 `.env`；避免打包进客户端导致反编译泄露。
5. **HarmonyOS 媒体限制** → 相册图片上传云端后用 URL 展示；本地视频复制进沙箱后用绝对路径喂给 `Video` 组件，规避临时 uri 失效。
6. **生产环境保护** → 所有后端改动先备份、先迁移再部署代码（避免"代码引用了尚不存在的列"导致现网 500），并做回归验证。

## 五、工程化

- **headless 编译校验**：用 DevEco 自带工具链 `hvigorw --no-daemon assembleHap` 做无界面编译检查。
- **单元测试**：`DateUtil` / `ScheduleService` / `Validator` 纯逻辑测试。
- **代码规范**：`code-linter.json5`（`@performance` + `@typescript-eslint` + `@security`）。
- **双仓库协作**：鸿蒙端与后端分别提交，提交信息均不含任何密钥。

## 六、可扩展方向

- 已登录态下的"修改密码"接口；
- 视频上云与多端共享；
- 蜕皮/环境/待办模块上云，彻底统一数据源；
- 离线缓存与双向同步（当前为纯在线优先）。
